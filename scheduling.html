Scheduling APIs

Partners read availability. They never become the calendar.

A vendor-neutral public contract already exists. Practice websites and marketplace partners consume it. Staff remain the authority. BookingRequest is not an Appointment.

The contract

Two public resources. One engine.

Every calculation flows through ISchedulingAvailabilityService in SchedulingService. There is no parallel availability engine. A channel adapter — including a Zocdoc adapter — plugs in over the same service.

GET /api/public/v1/availability

JSON slots

Practice timezone (for example America/Phoenix). Zone-offset start and end. durationMinutes. Each slot carries an opaque, encrypted availabilityToken. Query by public slugs — providerId, locationId, appointmentTypeId — not database ids.

GET /api/public/v1/availability.ics

iCalendar feed

The same free time as the JSON resource. Only free and bookable slots are exposed. A booked or blocked period simply yields no slot.

Booking intent

POST returns 202. Staff approve later.

POST /api/public/booking-requests
Authorization: Bearer    # or X-Api-Key

{
  "name": "Jane Doe",
  "phone": "480-555-0100",
  "email": "jane@example.com",
  "patientRelationship": "Existing",
  "preferredStart": "2026-08-20T21:00:00Z",
  "durationMinutes": 60,
  "reason": "New patient exam",
  "availabilityToken": ""
}

→ 202 Accepted  { "status": "accepted", "eventId": "…" }

Revalidation

Submitting a token re-runs the engine server-side. If the slot was consumed, the API returns 409 Conflict. Previously loaded availability is never treated as authoritative.

No PHI read path

IntakeService validates and publishes BookingRequestedEvent. It cannot read appointments or patient records. It stores only a minimized durable inbox row.

Staff remain the calendar

SchedulingService consumes the event and creates a BookingRequest. Staff match or create the patient, then approve and schedule — or reject.

Failure behavior

The website keeps working.

The topic decouples the website from the scheduler.

ConditionIntake responseWhat happens
Public booking disabled404Default. Nothing is internet-reachable until you turn it on.
Missing or wrong API key401Compared in constant time. Bearer or X-Api-Key.
Rate limit429Fixed window, 5 requests per minute per client IP. Forwarded addresses honored only from TrustedProxies.
Stale slot409Caller reloads availability. No silent overwrite.
SchedulingService down202Event waits in the scheduling subscription. No booking is lost. The website is unaffected.
Service Bus unreachable503No false 202. The calling website falls back to its own path (email).
Zocdoc

A channel adapter. Not a partnership claim.

Zocdoc work is a scheduling-API pilot. It is not a certified partnership. The adapter sits on the same public contract. It never becomes a second calendar and never sees PHI.

The first reference integration is documented on the Pilot page. No practice name or internal patient, provider, or location identifier is coupled to the intake workflow. CORS is not required — the website calls IntakeService server-to-server.

The process

From first call to a scoped channel.

Evaluate the source yourself. Then we scope a public-intake channel for one practice.

1 · Align on scope

We map the practice calendar, website, and any marketplace channel. We agree what IntakeService will expose — and what it will not.

1–2 weeks

2 · Enable public intake

API key, rate limit, practice timezone, booking horizon. Disabled by default until you turn it on. The website keeps an email fallback.

1–2 weeks

3 · Pilot a channel

Staff review booking requests in the portal. Partners stay on the public contract. The calendar remains the practice’s.
